## Sub-step loop of `FUN_001340D8` (once per physics step)
`dtTick = 1/50`; `rem = 1`; at most 2 iterations. Each: save the body (`FUN_00238BC8`), compute the contact points at the start pose (`FUN_001348A0`), **integrate the remaining step** `FUN_00238818(dtTick·rem)`, zero force/torque (`FUN_00237C78`), compute the end points, sweep (`FUN_0021A908`), take the first hit (`FUN_00217450`). No hit → done. If this was the 2nd iteration the hit fraction is forced to −1 *without restoring* (→ depenetration); otherwise restore (`FUN_00238C60`). `frac < 0` → depenetrate (`FUN_001344F0`). Else, for each hit in order: integrate `dtTick·rem·frac` (force is already 0 here), call the response `FUN_001344D0(module, hit, point)`; if it responds: `rem −= rem·frac` (the decompiler shows `(int)f * (f >= 0)`, read as a clamp to ≥ 0 — **hypothesis**) and continue with the next iteration; if no hit responds: restore and integrate the full remaining step. Ported as `integ::tick(...)` with callbacks (sweep / depenetration / response), no geometry inside.

**Finding:** `iw = sp·R = D·Rᵀ·R = D` for any orthonormal `R`: the engine integrates the angular velocity with the **body-frame diagonal inertia applied to L without rotating it** (ω = D·L, L being the stored vector). Faithfully ported (`updateDerived`).
**Not validated (see the free-flight section below for the partial result):** the position/orientation update itself (`pos += dt·vel`, `R[i] += dt·ω×R[i]`, the PMMI transpose direction — chosen because it is the physically consistent one: the other direction would rotate the opposite way), the force/torque magnitudes, the sub-step loop.
**Discrepancy (open):** the tail `node = pos − com·R` does **not** hold in the saved states: `|node − (pos − com·R)|` = 560 … 10 000 in every rider. The momenta/velocities are consistent, the stored `+0x50` is not tied to the node. Slots 05 and 10 (same race, node moved 25 u, HUD 1 s apart) have **identical** body fields (`tools/integrator_check.py 05 10`: displacement 0 in all riders; only 8 bytes of the module differ). **Hypothesis:** in these snapshots the player/AI nodes are driven by something other than the physics (replay/ghost or scripted intro) or the body is only live in other game states; nothing here confirms that the module integrated in these states. Slots 01–04 and 06–09 are byte-for-byte the same state (an earlier `pine_capture.py` run overwrote slots 2–9, per `docs/p2s-savestates.md`).

## Free-flight validation (2026-10-03) / Validación en vuelo libre

**EN.** *Partially validated: free flight only; the integrator does NOT count as validated (progress counter unchanged).*
- **Where the body is live.** The physics module (`rider + 0x6420`) is integrated only in ~1.2 s windows (impacts, "GOLPE"); while active, `module + 8` holds the node pointer. Outside those windows the game moves the node by other means and the body fields stay frozen (this explains the "frozen body" in savestates 05/10 and the failed `node = pos − com·R`). `tools/pcsx2/air_capture.py` waits for that link, lifts the body in +z through PINE (one 32-bit write per component, same burst for optional `--omega`/`--vel`) and records 50 consecutive game ticks; the game integrates by itself (node recomputed).
- **The plan's F_eff criterion was wrong.** In free flight F_eff ≠ (0, 0, −m·g): the game damps the momenta **before** calling `FUN_00238818` and passes gravity as a force. Model (**ajuste empírico** / empirical fit, residual of Δv 2e-6): `P ← P·(1 − c·dt)`, `L ← L·(1 − cL·dt)`, then `FUN_00238818(F = (0, 0, −m·G))`. Hence `pos` and `R` use the already-damped velocity and ω, and `P += dt·F` comes after the position update, exactly the order traced from the disassembly (step 3 before step 5). ## Provenance resolved (2026-10-04) / Procedencia resuelta

**EN.** *Level 2 (provenance) of the free-flight model is closed from the disassembly; every address below is from the ELF.* Details of the module in `physics-module.md`.
- **Per-tick order, `FUN_00133fa8(module)` (calls `FUN_00134060` at 0x134008, then `FUN_001340D8` at 0x134010):** `FUN_00134060(module)`: (1) `FUN_00237C78(body)` zeroes force/torque; (2) `FUN_00237960(body, module+0x120)`: `P *= k` and `vel *= k` (xyz of body+0x60 and +0xC0); (3) `FUN_00237998(body, module+0x11C)`: `L *= k` and `ω *= k` (body+0x70, +0xD0); (4) `F = (0, 0, module+0x110 · G)` with `G = -96.6000061` and `FUN_00237C88(body, F)` adds it to the force accumulator (+0xE0). Then `FUN_001340D8` (sub-step loop, calls `FUN_00238818`). Matches the fitted order exactly.
- **c, cL.** Constants stored by `FUN_00133AB0` (module initialiser, called from `FUN_00133A58` at 0x133A8C): `+0x120 = 0x3F79999A = 0.975`, `+0x11C = 0x3F7CAC08 = 0.987`. The fitted c = 1.2500, cL = 0.6500 correspond to the **linear** form `c = (1 − f)·50` (1.24999, 0.65000); the logarithmic form `c = −ln(f)·50` proposed beforehand gives 1.2659 and 0.6543 and is **rejected** (it is not an exponential decay, the factor is applied as is every tick).
- **G.** Literal `lui at,0xC2C1; ori at,at,0x3334` at 0x1340A4 = **−96.6000061** (float32). `3 × 32.2f` in float32 is exactly `0x42C13334` = 96.6000061, bit-identical to the literal, and the fit gave 96.600 ± 1e-4. The earlier search failed because the sign is negative (`0xC2C1…`) and the mantissa ends in …34 (not …33). The `32.2f` at 0x136374 (function `FUN_00136330`) is **not linked** to this path by anything found (no call chain was traced); **hypothesis**: the designers wrote `3 × 32.2`; the "1 unit = 1/3 ft" reading is **not supported**: the default contact points in `FUN_00133AB0` (front (0, 2.5, −2.6), rear (0, −1.4, −2.8)) give a wheel separation of ≈ 3.9 u, not 10–11 (a real mountain bike has ≈ 1.1 m).
- Also: `module+0x110 = 100.0` (mass used for the weight), `+0x114 = 0.2` (restitution), `+0x118 = 0.28` (friction), `+0x124 = 3.0` (read nowhere in this path).
- **Consequence for `bike.hpp` (not modified):** its `g = 32.17 u/s²` and the use of 0.975 as *angular* damping (`bike-physics.md`) contradict the engine (g = 96.6; 0.975 is *linear*, 0.987 *angular*). They stay hypotheses of the playable approximation.
- **Status.** Level 1 passes (cross-validation) and level 2 is located for c, cL and G. Counting `FUN_00238818` as validated **for free flight** is proposed to the maintainer; `progress.json` is not changed. Contacts and impacts remain unvalidated.
